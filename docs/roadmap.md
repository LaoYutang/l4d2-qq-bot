# 整体规划

规划日期：2026-10-15。目标先跑通“群消息 → 查询 → QQ 原生 Markdown 卡片 + 动态按钮”，再逐项迁移原始项目 API。技术栈以最终选择的 Python 为准，保留 Docker 和 Git tag 自动打包要求。

## 产品与交互

主场景为 QQ 群中 @ 机器人。单服卡片展示别名、服务器真名、地图真名 / 代码、人数、延迟、玩家与在线时长；综合卡片保留配置顺序，显示各服状态与统计。离线和玩家信息不可用必须分开，不能把网络失败显示为“0 人”。

默认使用 QQ 原生 Markdown 卡片，连接按钮挂在同一条消息底部。文字可选取复制，按钮是真实 keyboard 字段。PNG 作为可选模式和离线预览；两种输出共用领域模型和脱敏逻辑。

用户已明确目标交互：`查询1服` 下方显示连接 1服的按钮，`查询2服` 下方显示连接 2服的按钮，跳转地址随本次匹配的服务器变化。原生正文和 keyboard 在同一次消息请求中发送；依据 `connect_base_url` 和匹配服务器的 address 生成 HTTPS URL，每服 connect_url 可以覆盖。按钮文字及目标均来自本次查询结果，不共享全局“当前服务器”变量，避免多人并发查询串服。

当前实现已切换为单条原生 Markdown 卡片与底部按钮，用户已在真实 QQ 群中确认收到。无需 PNG 托管或 Markdown 模板。基础域名由维护者自定义，例如 `https://steam-connect.laoyutang.cn`，自动附加 `/IP:端口`。

官方普通按钮模板暂不支持变量，动态跳转使用 `keyboard.content` 自定义按钮，跳转 action.type=0、action.data 为目标 URL。其他应用的按钮权限仍需单独核实。使用 HTTPS 连接页，由该页提供打开 Steam / 复制 connect 指令；QQ 客户端直接支持 `steam://` 的情况不作保证。平台拒绝按钮时保留原生正文并明确提示，Markdown 也被拒绝时再回退文字。刷新、列表翻页等高级交互放在 M4。

未配置群不响应；服务器名 / 别名忽略空白并大小写归一，未唯一匹配时不执行操作。管理命令只精确匹配。分页和补充文字合计不得超过 QQ 当前被动回复配额；总览超过一批时通过下一条命令 / 按钮翻页。

## 阶段与交付门槛

### M0：规划与初始化（本次）

- [x] Python 包、uv、配置示例、AGENTS.md、架构与功能对照。
- [x] 命令解析、纯领域模型、本地 A2S 查询与 PNG 渲染。
- [x] 模拟 QQ 群事件串联命令解析和卡片生成；覆盖在线 / 离线 / PLAYER 失败。
- [x] WS 协议状态模型和离线测试；不宣称已建立真实连接。
- [x] Dockerfile、PR / 分支 CI、tag → GHCR 多架构镜像工作流。
- [x] 用户明确验收方向：原生卡片，底部挂载动态连接按钮。
- [ ] 迁移范围与其余 API 逐项验收。

### M1：QQ 端最小闭环

当前代码进度：Token 缓存、WS 登录 / 心跳 / 恢复重连、群隔离、发现 OpenID、队列与去重、原生 Markdown 卡片与动态按钮、可选 PNG 上传、查询 / 总览 / 地址 / 帮助均已实现。71 项离线测试通过，覆盖本机假 QQ HTTP/WS 的完整链路、同条消息的键盘、并发按钮目标与权限拒绝。真实 QQ 已验证鉴权、WS、PNG 回复；用户进一步确认原生卡片和底部按钮显示。群测仍使用模拟数据，真实游戏服务器数据、链接点击后的客户端唤起和长期稳定性仍需实测，因此不把整个 M1 标记为完成。

先使用真实 QQ 应用核实 WS 接入资格及群事件权限。实现 Token 缓存与刷新、GET /gateway、Hello / Identify / READY、心跳 ACK 检测、Resume、退避重连。读事件任务与有界业务队列分离。

原生卡片和可选文件上传已接上查询、connect、总览、地址、帮助。正文长度、图片与分页有上限；每条原始消息分配递增 msg_seq；去重缓存有 TTL / 容量限制；对平台 429 退避，不无条件重发有副作用操作。

继续验证“查询1服 → 连接1服的 HTTPS 页面”“查询2服 → 连接2服的 HTTPS 页面”的实际点击，以及不同群、多人并发、重复点击。当前纯 Markdown 原生卡片没有图片托管依赖。未来若加入图片资源，必须使用 QQ 可访问的 URL，不能用本地路径或 file_info 代替。

**完成条件**：真实群中连续查询成功；断线可恢复；一台服务器超时不影响其他卡片；重复事件不会重复回复；超长结果在配额内分页；日志无凭据。完成前不将镜像标为可正式部署的完整机器人。

### M2：补全查询生态

接入地图真名、黑盒语音、工坊和旧配置导入。共用 aiohttp 会话、独立超时、有界缓存。工坊对私有 / 不可下载条目提供明确状态。旧配置导入产生新文件和待人工映射的 OpenID 清单，不自动覆盖。

**完成条件**：相关接口使用可复现 fixture / mock 测试；外部服务失效时主查询仍可用；单品和合集、语音无人在线与失败均可区分。

### M3：管理与面板迁移

实现 RCON、重启、闪传及面板 API。会话键必须包含 group_openid + member_openid，覆盖并发、取消、超时、重复事件。只向本群明确配置的服务器提交任务，凭据不进入卡片。必要确认在用户对话中展示具体服务器与动作。

**完成条件**：非管理员永远无法触发网络管理操作；重放不会重复重启 / 安装；仅允许 `.vpk/.zip/.rar/.7z`；面板失败可区分于任务已经提交；审核和日志可定位操作。

### M4：发布稳定性与体验

完善刷新 / 翻页等高级按钮、可观测性、健康检查、配置热加载、镜像升级与回滚、依赖更新。再评估 C2C / 频道和持久化需求，避免在初始化引入不必要服务。

**完成条件**：linux/amd64 和 linux/arm64 真机 / CI 冒烟，容器非 root，SIGTERM 能关闭任务；稳定 tag 更新 latest，预发布不更新 latest；提供用户部署文档与已知限制。

## 关键决策

1. 默认 QQ 原生 Markdown + keyboard，不依赖浏览器渲染或图片托管；可选图片使用 Pillow 和 Noto CJK，不在图片里放假的可点击按钮。
2. QQ 传输与查询业务隔离。遵循 WS 要求，预留未来适配器；不在初始化偷偷切到 Webhook。
3. 原始 QQ 号 / 群号不能替代官方 OpenID，迁移时必须重新绑定。
4. 原项目的展示方式可调整，API 和管理员边界要保留。尚未迁移的命令不出现在“已可用”列表。
5. 用户已授权并完成真实 QQ 群测，当前保持模拟数据模式便于验收。真实服务器查询、管理操作、发布分别按其验收范围推进，不自动发送 RCON、安装地图或发布 tag。
